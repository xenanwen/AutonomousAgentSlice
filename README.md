# Autonomous Agent Slice

A minimal but real slice of an autonomous AI agent.

A person gives the agent a goal in plain language. The agent plans the work, executes a short sequence of steps using a mocked tool, tracks progress, and returns a finished result — with exact credit accounting, a hard execution limit, durable state, and safe retries.

The model and the tools are **mocked on purpose**. The point of this project is reliable agent *execution*, not model integration. Mocked tools are also deterministic, which is what makes the test suite reproducible.

## Architecture

```text
Browser  (index.html + app.js)
   |
   |  HTTP + JSON   (POST /runs, then poll GET /runs/{run_id})
   v
FastAPI  (backend/main.py)          <- HTTP only: validate, status codes, error shape
   |
   v
Run Service  (backend/run_service.py)   <- the rules: idempotency, run creation, execution
   |
   +---- Agent Loop  (backend/agent/loop.py)   <- bounded while-loop, credits, failure
   |        |
   |        +---- Mock Planner  (backend/agent/planner.py)   <- goal -> list of steps
   |        |
   |        +---- Mock Tools    (backend/agent/tools.py)     <- fake_search, fake_writer
   |
   +---- SQLite  (backend/models.py, backend/database.py)
            |
            +---- runs
            +---- steps
            +---- idempotency_records
```

The rule the layering follows: **HTTP code knows nothing about agents, and agent code
knows nothing about HTTP.** The run service is the seam between them. Swapping the mocked
planner for a real LLM call would touch exactly one file.

### Database schema

```text
runs
  run_id        TEXT  PRIMARY KEY
  goal          TEXT  NOT NULL
  status        TEXT  NOT NULL     queued | running | completed | failed
  current_step  INT   NOT NULL     how many steps have been started
  max_steps     INT   NOT NULL     the bound, copied onto the row for auditability
  planned_steps INT   NOT NULL     how many steps the planner wanted
  credits_used  INT   NOT NULL
  output        TEXT               set only on success
  error         TEXT               set only on failure
  created_at, updated_at
  CHECK (credits_used >= 0)          CHECK (credits_used <= max_steps)
  CHECK (current_step >= 0)          CHECK (current_step <= max_steps)
  CHECK (status IN ('queued','running','completed','failed'))

steps
  step_id      INTEGER PRIMARY KEY AUTOINCREMENT
  run_id       TEXT  NOT NULL  REFERENCES runs(run_id) ON DELETE CASCADE
  step_number  INT   NOT NULL  (1-based)
  name         TEXT  NOT NULL  planning | search | analyze | summarize | write_result
  status       TEXT  NOT NULL  pending | running | completed | failed
  detail       TEXT            short human-readable result
  error        TEXT            set only when this step failed
  started_at, finished_at
  UNIQUE (run_id, step_number)

idempotency_records
  key        TEXT PRIMARY KEY          <- uniqueness is enforced by the database
  run_id     TEXT NOT NULL REFERENCES runs(run_id)
  goal       TEXT NOT NULL             <- lets us detect a key reused for a different goal
  created_at
```

### Run state machine

```text
queued ---> running ---> completed        (the plan finished inside the budget)
                |
                +------> failed           (a tool raised, or max_steps_exceeded)

completed and failed are TERMINAL.
A terminal run is never executed again, never mutated, and never charged again.
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --reload
```

**Windows (PowerShell)**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1

```

small note: python 3.11/3.12 are the tested versions 

Then open <http://localhost:8000> in a browser. If you do that and the terminal says "WARNING: Invalid HTTP request received." then, open <http://127.0.0.1:8000> in a browser instead. The frontend is served by the same FastAPI process as the API, so there is no separate frontend server and no CORS setup.

Interactive API docs (generated by FastAPI) are at <http://localhost:8000/docs>.

The SQLite file `agent.db` is created automatically on first startup. Delete it to start from a clean slate.
```bash
python -m pytest tests/ -q
```

## API documentation

### `POST /runs` — start a run

Header (**required**):

```http
Idempotency-Key: abc123
```

Body:

```json
{ "goal": "Research Python" }
```

Response `201 Created` (a new run was created) or `200 OK` (this key already had a run —
a replayed request):

```json
{
  "run_id": "run_30ebe7d0111b",
  "goal": "Research Python",
  "status": "queued",
  "current_step": 0,
  "max_steps": 5,
  "credits_used": 0,
  "output": null,
  "error": null,
  "created_at": "2026-08-19T04:09:23.825909",
  "updated_at": "2026-08-19T04:09:23.825915",
  "steps": [
    { "step_number": 1, "name": "planning",  "status": "pending", "detail": null, "error": null },
    { "step_number": 2, "name": "search",    "status": "pending", "detail": null, "error": null },
    { "step_number": 3, "name": "summarize", "status": "pending", "detail": null, "error": null }
  ]
}
```

> **Note on `status: "queued"`.** `POST /runs` returns as soon as the run is persisted and
> hands execution to a background worker thread; the client then polls `GET /runs/{run_id}`.
> This is deliberate — the assessment also requires the user to *watch the steps appear*,
> and if POST blocked until the run finished there would be nothing to watch. It is also
> how real agent APIs behave, because real runs take minutes. The finished run, in exactly
> the shape the brief describes, is returned by `GET`.

### `GET /runs/{run_id}` — read a run

Returns the persisted run and all of its steps. This is the endpoint the frontend polls
every 500 ms while the run is `queued` or `running`, and stops polling as soon as the run
is `completed` or `failed`.

### Errors

Every error has the same JSON shape — never a stack trace:

```json
{ "error": "run_not_found", "message": "No run with id 'run_nope'." }
```

| Situation | Status | `error` |
|---|---|---|
| Missing / empty / whitespace-only goal | `400` | `invalid_request` |
| Goal longer than 2000 characters | `400` | `invalid_request` |
| Missing `Idempotency-Key` header | `400` | `missing_idempotency_key` |
| Unknown run id | `404` | `run_not_found` |
| Same key reused with a **different** goal | `409` | `idempotency_key_reused` |
| Unexpected server error | `500` | `internal_error` |

Full details (including the traceback) are written to the server log; the client only ever
sees the message.

### Demo triggers

Because the tools are mocked, failures are triggered by phrases in the goal:

| Goal contains | Effect |
|---|---|
| `force failure` or `FAIL_TOOL` | `fake_search` raises → the run fails at step 2 |
| `fail_writer` | `fake_writer` raises → the run fails at the last step |
| `never finish` / `loop forever` / `unbounded` | the planner produces an 8-step plan → `max_steps_exceeded` |
| `analyze` / `analysis` / `compare` | a longer 4-step plan (planning → search → analyze → write_result) |

The UI exposes the first one as a **"Force mock tool failure"** checkbox and the others as
one-click example chips.

## Design decisions

### Maximum step limit

`MAX_STEPS = 5` (in `backend/config.py`).

> **Every run has a hard maximum number of executable steps (change this if you want). If the agent reaches the limit
> without completing, the run transitions to FAILED with `error = "max_steps_exceeded"`, and
> no additional steps are attempted.**

It is enforced in three independent places, so no single bug can defeat it:

1. Only `min(len(plan), max_steps)` step rows are ever created, so the loop physically
   cannot iterate further.
2. The loop re-checks `current_step >= max_steps` before charging each step.
3. The database has `CHECK (credits_used <= max_steps)` and `CHECK (current_step <= max_steps)`.

Because the planner does not know about `MAX_STEPS`, the run also records `planned_steps`.
If `planned_steps > max_steps` the plan could never have fit in the budget, and the run ends
as `max_steps_exceeded` even if every executed step succeeded.

### Credit policy

`STEP_COST = 1`, and `credits_used` is an **integer**.

> **A credit is charged when a step *begins*. A failed tool call still consumes that step's
> credit, because the system has already attempted the work. Earlier credits are never
> refunded.**

So:

```text
Step 1 succeeds  = 1 credit
Step 2 succeeds  = 1 credit
Step 3 fails     = 1 credit
-------------------------------
credits_used     = 3
```

Integers, not floats: credits are a money-like counter, and floating point drifts
(`0.1 + 0.2 != 0.3`). An integer count of steps is exact, is directly comparable against the
bound, and can be reconciled by eye — three step rows, three credits. The invariant
`credits_used == number of steps started` holds for every run in the database, successful or
not.

### Failure semantics

A failed run is **evidence, not garbage**. When a step fails, the system keeps:

- every earlier completed step and its result,
- the failed step, with its own error message and timestamps,
- the exact number of credits already consumed,
- the run-level failure reason (`tool_failed: ...` or `max_steps_exceeded`).

Nothing is erased, nothing is refunded, and the run is never marked completed. It stays in
SQLite so it can be inspected later, and `GET /runs/{run_id}` returns everything the
frontend needs to explain what happened.

There are exactly two failure reasons, both terminal:

- `tool_failed: <message>` — a tool raised during a step.
- `max_steps_exceeded` — the plan did not fit inside the budget.

An unexpected bug in our own code is caught too and recorded as `internal_error`, so a crash
still leaves an accurate record rather than a run stuck in `running` forever.

### Retry and recovery

Failed runs are **not** retried automatically. The original run is preserved, and the client
starts a new one:

```text
run_123 -> FAILED      (kept forever, still readable via GET /runs/run_123)
retry   -> run_124     (a new run, a new idempotency key, its own credits)
```

The old run is never silently mutated into the new one. That keeps the audit trail honest:
if a customer was charged 3 credits for a failed run, that record still exists.

### Idempotency

The client sends an `Idempotency-Key` header. The first request creates the run and stores
`key -> run_id`. Any later request with the same key returns that same run without creating
a second one, executing the agent again, or charging a single extra credit.

```text
Idempotency-Key: abc123          Idempotency-Key: abc123   (retry)
        |                                |
        v                                v
   no record yet                   record already exists
        |                                |
        v                                v
   create run_123                   return run_123
   store abc123 -> run_123          201 becomes 200 - no execution, no charge
```

**The concurrency part is the important part.** This implementation deliberately does *not*
do:

```python
if key not in database:      # <-- two simultaneous requests can BOTH pass this
    create_run()
```

Instead it optimistically INSERTs, and lets the **PRIMARY KEY on `idempotency_records`**
reject the loser:

```python
try:
    session.commit()               # run + steps + idempotency record, one transaction
except IntegrityError:             # someone else won the race
    session.rollback()
    return existing_run_for(key)   # treat duplicate-key as "this request already has a run"
```

The database's uniqueness constraint *is* the lock, and it is atomic, so exactly one request
can ever win — no Redis, no distributed lock manager. The run, its step rows, and the
idempotency record are committed as a single transaction, so it is impossible to end up with
a run that has no key or a key that points at nothing.

The record lives in SQLite rather than in memory, so **restarting the server does not lose
the protection** (there is a test for exactly that).

Reusing one key for a *different* goal returns `409 Conflict`. That is a client bug, not a
retry, and silently returning the old run would hide it.

### Why SQLite

The requirements are: survive a restart, enforce uniqueness atomically, and be trivial to
run locally. SQLite does all three with zero setup — it is a file. A hosted Postgres would
add operational complexity without changing a single line of the reliability logic, and the
SQLAlchemy models would port to it essentially unchanged.

### Why the model and tools are mocked

The assessment explicitly asks for it, and it is the right call anyway: a real LLM or search
API would make the tests non-deterministic and the failure scenarios unreproducible. With
mocks, "step 3 fails and 3 credits are consumed" is a fact I can assert in a test rather than
a thing I hope happens.

## Required walkthrough

All three scenarios below are real output, captured from a running server.

### Scenario 1 — a successful run

**Request**

```bash
curl -i -X POST localhost:8000/runs \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-success-1' \
  -d '{"goal":"Research Python"}'
```

**Response** — `HTTP/1.1 201 Created`

```json
{
  "run_id": "run_30ebe7d0111b",
  "goal": "Research Python",
  "status": "queued",
  "current_step": 0,
  "max_steps": 5,
  "credits_used": 0,
  "steps": [
    { "step_number": 1, "name": "planning",  "status": "pending" },
    { "step_number": 2, "name": "search",    "status": "pending" },
    { "step_number": 3, "name": "summarize", "status": "pending" }
  ]
}
```

**Mid-run poll** — `GET /runs/run_30ebe7d0111b` while the agent is working:

```json
{
  "status": "running",
  "current_step": 2,
  "credits_used": 2,
  "steps": [
    { "step_number": 1, "name": "planning", "status": "completed",
      "detail": "Planned 3 steps: planning -> search -> summarize" },
    { "step_number": 2, "name": "search",   "status": "running" },
    { "step_number": 3, "name": "summarize","status": "pending" }
  ]
}
```

**Final state** — `GET /runs/run_30ebe7d0111b`

```text
status        completed
credits_used  3
error         null

step 1  planning   completed   Planned 3 steps: planning -> search -> summarize
step 2  search     completed   Search returned 3 results for 'Research Python'.
step 3  summarize  completed   Wrote the final answer (286 characters).
```

**Final output**

```text
Summary for goal 'Research Python':

Python is a general-purpose subject with broad practical use. Python is commonly used in
professional software development. Python is widely discussed in data and research contexts.

Conclusion: Python is well documented across the sources reviewed.
```

**Credits: 3.** Three steps were started, so exactly three credits were charged.

### Scenario 2 — a duplicate request

The exact same request, sent twice with the exact same idempotency key.

```bash
# first request
curl -X POST localhost:8000/runs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-retry-9' -d '{"goal":"Research Python"}'

# second request - identical body, identical key
curl -X POST localhost:8000/runs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-retry-9' -d '{"goal":"Research Python"}'
```

```text
First request:   HTTP 201   run_id = run_267ed49f4697   credits = 3 (once finished)
Second request:  HTTP 200   run_id = run_267ed49f4697   credits = 3
```

**The second request did not create another run and did not execute the agent again.**
It returned the existing run, so no second credit charge occurred: the total is still 3, not
6. The `201` vs `200` status code is how the client can tell a fresh run from a replay.
`SELECT COUNT(*) FROM runs` confirms exactly one row (asserted in the test suite).

Reusing the same key with a different goal is rejected instead of silently returning the
wrong run:

```bash
curl -X POST localhost:8000/runs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-retry-9' -d '{"goal":"Research Rust"}'
```

```text
HTTP 409
{"error":"idempotency_key_reused",
 "message":"This Idempotency-Key was already used for a different goal. Use a new key for a new request."}
```

### Scenario 3 — a tool failure

```bash
curl -X POST localhost:8000/runs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-fail-9' -d '{"goal":"Research Python and fail_writer"}'
```

Final state:

```text
step 1  planning   -> SUCCESS   Planned 3 steps: planning -> search -> summarize
step 2  search     -> SUCCESS   Search returned 3 results.
step 3  summarize  -> FAILURE   Mock writer tool failed: simulated model timeout.

status        failed
error         tool_failed: Mock writer tool failed: simulated model timeout.
credits_used  3
output        null
```

**What happens to the state:** nothing is erased. Steps 1 and 2 keep their `completed`
status, their results and their timestamps. Step 3 keeps its `failed` status and its error
message. The run is marked `failed` with the reason, and it stays in SQLite permanently for
debugging and auditing.

**What happens to the credits:** all three are kept. Step 3 was attempted, so its credit was
charged before the tool ran, and a failure does not refund it — nor does it refund steps 1
and 2. `credits_used = 3`.

**Retrying** does not touch this run. The client starts a new run with a new key, which gets
its own `run_id` and its own credits, while the failed run remains available.

The mid-run variant (`"Research Python and force failure"`, which fails the *search* tool at
step 2) shows the same semantics with 2 credits: step 1 completed, step 2 failed, step 3
never attempted and therefore never charged.

### Bonus scenario — the execution limit

```bash
curl -X POST localhost:8000/runs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-max-9' -d '{"goal":"Research Python and never finish"}'
```

The planner proposes 8 steps; the budget is 5.

```text
step 1  planning  completed
step 2  search    completed
step 3  analyze   completed
step 4  search    completed
step 5  analyze   completed

status        failed
error         max_steps_exceeded
credits_used  5 / 5
output        null
```

The run stops immediately at the bound. Credits stop at 5 and never increase afterwards.

## Tests


The tests drive the real HTTP API and poll for completion exactly the way the browser does,
so they exercise the production code path rather than calling internals.

| Requirement | Test |
|---|---|
| 1. Successful execution | `test_successful_run`, `test_analysis_goal_uses_a_longer_plan` |
| 2. Max-step protection | `test_max_steps_protection`, `test_credits_stop_increasing_after_the_limit` |

| 5. Different keys → different runs | `test_different_keys_create_separate_runs` |
| 6. Persistence across a restart | `test_run_survives_an_application_restart`, `test_idempotency_survives_a_restart` |

`test_run_survives_an_application_restart` disposes the entire connection pool, rebuilds the

is what proves the state lives on disk and not in the process.

Verified manually as well, against a live `uvicorn` server driven by a real Chromium browser:
progress rendering, success rendering, failure rendering, the idempotent replay button, and a
clean browser console.

## How I would explain this project in an interview

> I built a working slice of an autonomous agent: you give it a goal in plain language, it
> plans a sequence of steps, executes them with a tool, and returns a result — with exact
> credit accounting and safe retries. The model and tools are mocked on purpose, because the
> interesting engineering here is reliable execution, not model integration, and mocking makes
> every scenario reproducible in tests.
>
> The architecture is four layers: FastAPI handles only HTTP, a run service owns the business
> rules, an agent loop does the work, and SQLite persists everything. The layers don't leak —
> the agent code has no idea HTTP exists — so I could swap the mocked planner for a real LLM
> call by changing one file.
>
> The agent loop is a bounded `for` loop over a plan the planner produced. For each step it
> charges the credit, marks the step running, commits, executes the tool, and commits the
> result. It commits after every state change, which is what lets the browser poll and watch
> steps light up one at a time — and it means a crash leaves an accurate record instead of a
> lie.
>
> Runaway execution is prevented by a hard bound of five steps, enforced in three independent
> places: I only ever create step rows for steps I'm allowed to run, the loop re-checks the
> bound before charging, and the database has a CHECK constraint that credits can never exceed
> max_steps. If the plan is longer than the budget, the run ends as `max_steps_exceeded` and
> stops immediately.
>
> Partial failure is treated as evidence rather than garbage. If step three's tool raises, the
> completed steps, their results, the failed step's error, and the exact credits already spent
> all stay in the database. The run is marked failed with a reason; it's never erased and never
> auto-retried. Retrying means creating a new run, so the failed one stays auditable.
>
> Idempotency is the part I'm most careful about. The client sends an `Idempotency-Key` header,
> and I store that key with a uniqueness constraint in SQLite. I deliberately don't do a
> check-then-insert, because two concurrent retries could both pass the check — instead I
> attempt the insert inside one transaction with the run itself and catch the integrity error,
> so the database's uniqueness constraint is the lock. The loser of that race just returns the
> run that already exists. Because the record is on disk, the protection survives a restart,
> and there's a test for that.
>
> Credits are integers, never floats, because they're a money-like counter and floats drift.
> One credit per step, charged when the step begins, so a failed step still costs its credit —
> the work was attempted. The invariant is that credits always equal the number of steps
> started, which means I can reconcile any run by eye.
